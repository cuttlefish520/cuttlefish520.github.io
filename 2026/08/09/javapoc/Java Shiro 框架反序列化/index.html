Apache Shiro 是一个强大且灵活的Java安全框架，用于处理身份认证、授权、密码加密、会话管理 等功能。

在shiro版本小于1.2.5时，被称作shiro-550，shiro反序列化的产生原因主要是因为rememberMe内容，原因是AES密钥被硬编码在shiro源码中，导致在cookie中的rememberMe可以被插入恶意代码造成代码执行。在1.2.5之后，shiro使用了随机密钥，又因为padding oracle attack导致反序列化，被称作shiro-721。

漏洞描述

shiro提供的Remember Me功能，在用户登录成功后会生成一个加密并编码后的cookie，而功能实现是服务器获得字段为Remember me字段的cookie, 解码解密后进行反序列化恢复用户，但cookie的加密密钥被硬编码在了shiro的源码里，这就导致cooike可以传入攻击者构造的恶意类，从而实现命令执行

漏洞分析

web.xml

web.xml 是 Java Web 应用的标准部署描述文件，是 Servlet 规范定义的核心配置文件，通常放在项目的 WEB-INF 目录下。Tomcat、Jetty 等 Web 容器启动应用时，会优先读取并解析这个文件，以此完成整个 Web 应用的组件注册、行为规则配置。这里就是声明了一个过滤器ShiroFilter,把后面所有路由都交给shiro处理（/*匹配全部路由）

shiro认证规则配置文件shiro.ini

这给/login.jsp登录路由配置了authc过滤器

这里请求表单上传到Tocat服务器，ShiroFilter 的父类是 AbstractShiroFilter，它的核心入口方法是 doFilterInternal，所有 Shiro 的安全逻辑都从这里开始。前面了解的获得remember me字段反序列化创建完Subject（用户主体）对象接着才回去authc过滤器进行验证。

先看登录逻辑

AbstractShiroFilter::doFilterInternal()

这里是shiro安全体系的执行入口，这里主要看两个部分

createSubject()

这里就是获取请求用户，构建用户主体，有Remember me那就会获取cookie字段，解码解密反序列化恢复用户

executeChain()

这是 shiro.ini 中 [urls] 规则的实际调度入口，也是 authc 等过滤器的执行起点：

  1. 根据当前请求的 URL 路径，匹配 [urls] 段的配置规则，取出该路径对应的过滤器列表（比如 authc, roles[admin]）；
  2. 按配置顺序组装成 Shiro 内部过滤器链，依次执行每个过滤器的校验逻辑；
  3. 所有内部过滤器全部校验通过后，调用原生的 FilterChain chain

那这里就会调用authc过滤器也就是org.apache.shiro.web.filter.authc.FormAuthenticationFilter类，那这里跟进去看这个类

  • token：用户登录时提交的令牌（如 UsernamePasswordToken）。

还有一个原因是shiro中的反序列化用的不是标准ObjectInputStream，而是 ClassResolvingObjectInputStream

我原链中InstantiateTransformer 的序列化数据中包含了 Class[]{Templates.class} 这个类型数组。在 Shiro 的 ClassResolvingObjectInputStream 中，反序列化过程中对 Class 类型的处理存在兼容性问题，会抛出类似以下错误：

这是因为 ClassResolvingObjectInputStream 重写了 resolveClass 方法，在处理嵌套的 Class 类型数组时，类型编码（Type Code）的读取方式与标准 ObjectInputStream 不一致，导致流解析中断。
